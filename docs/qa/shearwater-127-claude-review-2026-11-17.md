# Shearwater 작업127 검토 — 첫 사용·설명·작업 흐름 (Claude)

**범위**: 첨부된 7개 파일만 읽음. 브리프의 memdex 등록·route 전송은 실행하지 않음. `diagnostics.go`, `diagnostic_why.go`, `install.md`는 제공되지 않아 조회 도구의 실제 출력 형식은 미확인. 실행·측정은 하지 않음.

**연구 주장**: 논문 원문이 없어 **검증하지 못함**. 아래 논문 언급은 모두 내 기억에 의한 것이며 설계 가설로만 취급해야 함.

## 1. 지금 추천할 이유가 있나

**사실**
- README 첫 문단은 기능을 나열할 뿐 "Compose 대신 왜"에 답하지 않음. 스스로 "다른 도구보다 쉽다는 주장은 검증하지 않았어"라고 적음.
- `compatibility.md`: Service DNS·UDP·NodePort·PVC·RBAC 없음, securityContext는 저장만 함. 브리프: 이미지 빌드와 Compose 변환 없음.
- Service IP는 WSL 내부 주소라 Windows 브라우저에서 바로 열 수 없음(`first-try.md`).

**판단(추정)**: 앱 1~3개를 "운영"하려는 사람에게는 지금 추천하기 어려움. 추천할 수 있는 경우는 좁음.
- kubectl·Deployment 롤링과 이력을 가볍게 배우거나 실험하려는 경우.
- AI에게 읽기 전용 진단을 맡기고, 변경은 해시로 고정된 계획을 승인해 통제하려는 경우.

**Compose가 나은 경우**: 소스 빌드, 서비스 이름으로 통신, 포트 공개, 영속 볼륨, UDP, 실제 데이터가 필요할 때.
**기존 Kubernetes(k3s 등)가 나은 경우**: Helm 차트, Ingress·DNS·PVC·RBAC, 보안 정책 집행, 다중 노드가 필요할 때.

**제안**: README 상단에 "이럴 때 쓰고, 이럴 때 쓰지 마" 표를 넣기. 차별점은 "관측 → 계획 → 승인 → 영수증" 한 가지로만 주장하기.

## 2. 가장 큰 수작업 두 가지

### A. AI 연결 설정

**사실** (`agent-mcp.md`): 사람이 하는 일은 다음과 같음.
- Bash에서 sw 절대 경로 확인.
- PowerShell에서 배포판 이름 확인, `Read-Host`로 경로 입력, `claude.exe`/`.cmd` 선택.
- `mcp add` 실행 후 `/mcp`로 확인.
- 쓰기용은 `shearwater-write`로 한 번 더 등록.

**제안**: `sw mcp setup --client=claude-code [--allow-write]` 추가. 프로그램은 자기 경로와 배포판을 감지해 등록 명령 한 줄(또는 JSON)을 출력하고 initialize→tools/list 자가 점검까지 수행. 사람은 한 줄 붙여 넣고 도구 개수만 확인.

### B. 요청에서 결과 확인까지

**사실**
- AI가 전체 JSON 매니페스트를 작성해야 함. `sw_plan`은 `manifest: object`만 받음(`mcp.go`).
- 기존 객체는 PUT 전체 교체라 빠진 필드가 제거될 수 있음(`plan.go`의 `a.Method = "PUT"`, 문서 경고).
- 사람이 before/after 원문 JSON을 눈으로 비교함. `planPreview`는 body·before·after를 통째로 반환하며 요약 diff가 없음.
- 사람이 64자리 해시를 `--plan`과 `--confirm`에 두 번 입력.
- `executePlan`은 영수증만 반환함. 준비 상태와 HTTP 응답은 사람이 kubectl `rollout status`와 `curl`로 따로 확인.
- 삭제·정리는 kubectl로만 가능. namespace와 그 자식은 계획을 나눠야 함.

**제안 흐름**

| 단계 | 사람 | 프로그램/에이전트 |
|---|---|---|
| 요청 | "web을 1.28로 올려 줘" | 의도형 입력(이미지·복제본·포트)을 현재 객체에 병합해 계획 생성 |
| 검토 | 변경된 필드 3~5줄 요약 읽기 | 제거되는 필드를 경고로 표시 |
| 승인 | `sw approve` 실행 후 TTY에서 짧은 확인 | 대기 중인 계획 목록과 요약을 보여 주고, 내부에서는 정확한 해시에 결합 |
| 적용·확인 | 결과 읽기 | 적용 후 `sw_wait`류 도구로 rollout·Ready·엔드포인트 확인, 실패 시 why 근거 첨부 |

승인을 줄이는 것은 보안 약화가 아님. 문서가 이미 "같은 OS 권한의 다른 프로그램이 승인 파일을 만들 수 있다"고 인정함. 승인의 실제 가치는 사람이 변경 내용을 읽는 데 있고, 지금은 그 읽기가 가장 불편함.

## 3. MCP와 내장 대화의 공유 구조

**사실**: 코어는 이미 공유됨. `mcpCall`과 `runPlanCommand`가 같은 `preparePlan`/`executePlan`을 호출함.

**제안**: 공유할 것은 채팅이 아니라 "의도 → 계획" 함수 층. 내장 대화는 이 함수를 프로세스 안에서 부르는 얇은 루프로 한정.

**불필요하게 커질 부분**
- **모델·인증**: 다중 제공자 추상화와 키 저장소는 과함. 환경변수와 엔드포인트 하나면 충분. root로 도는 프로세스가 API 키를 들고 신뢰할 수 없는 앱 로그를 외부 모델로 보내는 구조는 로그 유출과 프롬프트 주입 위험이 있어, 모델 루프는 권한을 분리해야 함.
- **의존성**: SDK를 넣으면 README가 내세운 외부 모듈 46개, 바이너리 40MB 이하 목표와 충돌함. 평문 HTTP 사용 권장.
- **대화 이력·비용**: SQLite 스키마에 넣지 말 것. 세션 메모리와 기존 계획·영수증 파일이 감사 기록 역할을 함.
- **권한**: 승인 프롬프트는 모델이 만든 텍스트가 아니라 프로그램이 직접 렌더링하고 TTY 입력으로 받아야 함. 내장 대화에도 승인 도구는 두지 않음.

## 4. 반드시 구현할 것과 미룰 것

**먼저 (작은 것부터)**
1. **문서 버전 불일치 수정(사실)**: `first-try.md`는 제목과 성공 조건이 alpha.6인데 경로는 alpha.7이고, README는 alpha.7. 첫 사용자가 성공 조건 1번에서 막힘.
2. **도구 스키마 설명 추가(사실)**: `fieldType`이 type만 내보내 `resource`의 형식(`pod/NAME`)이 스키마에 없음. `sw_get`은 설명에도 없음.
3. **오류·절단 처리(사실)**: `text += callErr.Error()`가 구분자 없이 붙음. 절단은 `text[:256<<10]`로 앞부분만 남겨, 로그라면 최신 줄이 사라지고 UTF-8이 깨질 수 있음. 꼬리 보존과 오류 코드·복구 힌트 분리 필요.
4. 계획 요약 diff와 승인 UX 개선(2B).
5. 적용 후 관찰 도구, 영수증 조회 도구. 지금은 `uncertain-or-partial` 영수증을 MCP로 읽을 방법이 없음.
6. 의도형 계획(이미지 변경·scale·새 웹앱)과 삭제 계획.
7. 연결 설정 도우미(2A), README 선택 기준 표.

**뒤로**: 내장 대화(6번 이후 최소형으로), Compose 변환, 이미지 빌드, DNS, 다중 노드, 대화 이력 저장.

## 5. 관찰·행동 구조와 연구 근거 (모두 미검증 가설)

- **SWE-agent의 ACI** (기억): 간결한 피드백과 가드레일이 성능에 영향을 준다는 주장. 가설: 도구 결과를 `상태 / 핵심 근거 / 다음 가능한 행동` 구조로 줄이면 호출 수와 실패가 줄어든다.
- **Lost in the Middle** (기억): 긴 문맥 중간의 정보가 누락되기 쉽다는 주장. 가설: before/after 전체 대신 변경 필드 요약을 맨 앞에 두면 검토 오류가 줄어든다.
- **tau-bench** (기억): 반복 시행에서 일관성이 낮다는 주장. 승인을 유지하고 성공률을 1회가 아닌 k회 반복으로 재야 한다는 근거가 됨.
- **Miller/Cohen, Rao/Ballard**: 뇌과학 비유일 뿐 LLM 성능의 실증 근거가 아님. 설계 어휘로만 사용.
- **Lamport, Herlihy/Wing**: 현재 코드는 UID·resourceVersion 낙관적 검사를 쓰며, 여러 객체에 대해 원자적이지 않다고 문서가 명시함. 선형성 주장을 하려면 별도 시험이 필요.

## 6. 작은 검증안 (제안)

1. **에이전트 과제 5종**: 새 웹앱 배포, 이미지 변경, scale, 크래시 진단, 충돌 후 복구. 현재 도구와 개선 도구로 각 5회 반복. 성공률, 도구 호출 수, 응답 바이트, 사람 입력 횟수를 측정. `hack/mcp-check.py`의 별도 API를 쓰고 "에이전트 점검"으로 표기.
2. **Compose 동일 조건 비교**: 같은 3개 시나리오(배포, 잘못된 이미지 진단, 업데이트·되돌리기)에서 사람 명령 수와 원인 파악까지의 시간을 측정. 불리한 결과도 기록.
3. **외부 첫 사용자 3~5명**: `first-try.md` 기준 그대로, 설명 없이 첫 HTTP 응답까지의 도달률과 일주일 뒤 재사용 여부.

**통과 기준(제안)**: 사람 입력 단계가 절반 이하로 줄고, 반복 성공률이 떨어지지 않을 것.

**운영 주의**: 문서를 고치면 작업125 관측기의 해시·clean 전제와 충돌하므로, 수정 후 별도 정리가 필요함(브리프 명시).
